## 排查并处置 macOS 钥匙串弹框「找不到用于储存"Chrome"的钥匙串」

**现象**：用户截图一张系统级弹框（标题「找不到钥匙串」，正文「找不到用于储存"Chrome"的钥匙串。」，
按钮 取消 / 还原为默认），出现在 00:42 左右。

**结论（先说结论）**：钥匙串**没有坏**，不要点「还原为默认」。这是 Chrome 向系统索要钥匙串时
被 SecurityAgent 拦下的模态框，属可「取消」掉的良性弹框。

### 证据链

| 检查 | 结果 |
|---|---|
| `security default-keychain` | `/Users/yummy/Library/Keychains/login.keychain-db`（正确） |
| `security list-keychains` | login + openvpn + System.keychain，三条都存在 |
| `login.keychain-db` 文件头 | `kych` 魔数正常，306KB，`show-keychain-info` 秒回 `no-timeout` |
| 读写实测 | `add-generic-password` → `find-generic-password` → `delete-generic-password` 全程成功 |
| 系统日志 00:31 / 00:36 | `Google Chrome[41738/41782/41955] SecKeychainAddCallback` 之后约 140ms 拉起 `SecurityAgent[41788/41964]` |
| Chrome 版本 | 磁盘已装 `153.0.8010.54`，但主进程 pid 1651 从 **09-24 17:19** 起跑的还是 `.53` |

- **因果链**：Chrome 处于「已更新待重启」的版本错位态 → 它自己反复重启重试 →
  每次重启都重新索要 `Chrome Safe Storage` → 系统派 SecurityAgent 弹框（约 00:31、00:36 各一次）。
  日志里那几个进程带完整 GUI 栈（初始化 LocationManager / AppKit），不是我们的 headless 脚本。
- **验证**：00:31:28 与 00:31:43 两次启动相隔 15 秒，是自动重启的典型节奏。
- 弹框已不在屏幕上（`ps` 无 SecurityAgent 常驻）。

### 被自己实验否掉的假设（记下来，别再走一遍）

先怀疑是「我们的自动化脚本反复以全新 profile 起 Chrome，去碰真钥匙串」，于是做了 A/B：

| 条件 | SecKeychain 调用 | SecurityAgent 弹框 |
|---|---|---|
| `--use-mock-keychain --password-store=basic` | 5 次 | 0 |
| 不带这两个开关 | 5 次 | 0 |

**两组完全一致 → 该开关不是本次弹框的成因**。那 5 次 `SecKeychainAddCallback` 只是启动时的
常规注册，不代表真有存取动作。差点据此下错结论，靠对照组救回来了。

### 已做的改动与处置

1. `prototype/verify.py`：Chrome 启动参数加 `--use-mock-keychain --password-store=basic`
   + 注释说明原因（**预防性加固，不是本次根因**；仍是 macOS 上自动化跑 Chrome 的最佳实践）。
2. 技能 `static-prototype-verify`：新增 §3.0「会打断用户的副作用：macOS 钥匙串弹窗」，
   并给 4 处 Chrome 启动模板补上这两个开关。
3. 误操作已还原：查 `openvpn.keychain-db` 时误用 `security list-keychains -s <path>`
   （`-s` 是**设置**搜索列表，不是查看）→ 已用
   `security list-keychains -s login.keychain-db openvpn.keychain-db` 还原，复核为原来三条。
4. 自建测试条目 `wbkc-selftest` 已删除并复核（`find` 返 44 = 不存在）。

### 给用户的处置建议

1. 弹框出现时点**取消**；**不要点「还原为默认」**（会把自建钥匙串从搜索列表里摘掉）。
2. **彻底退出 Chrome（⌘Q）再重开**，让它从 `.53` 升到 `.54`，消除版本错位——这是复发的根源。
3. 若仍复发：钥匙串访问里删掉 `Chrome Safe Storage` 条目，重开 Chrome 自动重建。
4. 可选：`/tmp/figref/profile`（端口 9333）的 headless Chrome 从 11:04 起一直在后台跑，可关。

## v38 · 主页「问答交互」卡全屏（新一轮需求 1）

需求：主页的智能问答交互窗口加全屏图标，点击全屏、点缩小回原位。
v37 那次做的是**右下角浮窗**（`.agentwin.is-full`）；这次是**主页那张卡**（`#wbAgentCard`）——
同一份会话（`agentBoxes()`）的两扇窗，语义照抄，但宿主差一个关键点：浮窗本来就是 fixed，
卡片是页面流里的一格，`position:fixed` 一上身就**脱流**，右侧栏塌成 0、整页往上跳。

### 落地

| 点 | 做法 |
|---|---|
| CSS | `#wbAgentCard.is-full{position:fixed;inset:22px;z-index:58;display:flex;flex-direction:column}`；`.card__bd` 转 flex、`.wbagent__bd` 由写死 300px 松成 `flex:1`（实测 300→799）；气泡 `max-width:min(760px,92%)`；`body.is-wbfull` 藏浮球 + 锁 body 滚动 |
| 占位 | 进全屏时把父 `.stack` 的 `min-height` 记成卡片原高（523px），缩回清掉 —— 否则「缩回原位」实际是「缩回重排后的位置」 |
| JS | `toggleWbFull(force)`；接线：点击分支（`[data-wb-full]`）、`goto()` 复位、Esc 分层退出（先缩全屏，不收卡片）；进全屏前若浮窗开着先 `toggleAgent(false)` |
| z 取 58 | 与编排区全屏同档：高于顶栏 40，低于遮罩 60/抽屉 61/弹窗 70 → 全屏里再开弹窗天然压在上面，不必像浮窗那样在 `showModal()` 里挂一句「先缩回」 |
| 钩子 | `window.__wbFull(v)`（**不传参=纯读**）、`window.__wbBelow()`（量下方那张卡的 top，守「页面没被挤动」） |

### 验证
